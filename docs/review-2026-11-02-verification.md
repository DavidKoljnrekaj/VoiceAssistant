## Fix before merging

| Id | Where | Finding |
|---|---|---|
| V-1 | `fix/db-review`: `supabase/migrations/20261102100000_voice_calls_expiry_cap.sql`, `apps/api/src/voice/calls.ts` (`startCall`) | The new `CHECK (expires_at <= created_at + interval '15 minutes')` compares `expires_at`, which the API computes as `min(jwtExp, deps.clock() + 15 min)` on the **API host's clock**, with `created_at`, which defaults to the **database's** `now()`. If the API clock runs ahead of the database by more than the start's preceding round trips, every call start fails with 23514 → 500 `internal_error`, and the API suite cannot see it (the PostgREST fake enforces no CHECK). Fix: send `created_at: now.toISOString()` in the `voice_calls` insert so both sides use one clock (or compute `expires_at` in SQL); a test that pins the insert carries `created_at`. The migration header's "regenerate `database.ts`" line contradicts REL-7 (a CHECK changes no type) — drop it. |

## Real issues from the fixes

| Id | Size | Where | Finding |
|---|---|---|---|
| V-2 | Medium | `apps/voice/src/agent.ts:179`, `lifecycle.ts:43-46` (`HangUp.afterSpeech` / `spoke()`) | `spoke()` fires on **any** speaking → non-speaking transition, and LiveKit releases the agent state at the end of every speech. A goodbye (VOICE-11, the cap) or the error fallback (VOICE-12) requested while a previous answer is still draining is pre-empted by that answer's end: the worker hangs up before the line is synthesised. Reachable by a barge-in at the cap turn, or an STT/TTS error mid-answer. Fix: tie the hang-up to the *specific* `say()` handle (await its playout / `SpeechHandle` done) rather than to the next state change; keep the 10 s grace. Needs a test through the lifecycle seam that models two speeches. |
| V-3 | Medium | `apps/voice/src/session.ts:93` (`identity.ctx()` inside the serialised turn chain), `turn.ts:134` | VOICE-9 serialised turns, which put the untimed `identity.ctx()` network read (Supabase + GoTrue, no timeout) on every later turn's path, before the turn's 25 s timer exists. A hung identity read now stalls the whole call instead of one turn. Also a queued turn LiveKit already cancelled still counts against the 50-turn cap and does the identity read before `turn.ts:132` sees `signal.aborted`. Fix: bound the identity read with a deadline (as the API does with `withDeadline`), check the signal before counting the turn. |
| V-4 | Low, a decision | `apps/api/src/voice/calls.ts:63` vs `:69` | The R-A5 fix deletes the caller's previous `voice_calls` row **before** the rate-limit counts, so a *refused* start (429 `calls_per_day` or `concurrent_calls`) deletes a live credential and the caller's in-progress call is refused by the worker on its next identity re-read. Documented in `docs/API.md` as deliberate. Alternative that fixes R-A5 without the side effect: keep the delete after the counts and exclude the caller's own row from the concurrent count (`.neq('user_id', ctx.userId)`). Decide, record in the backlog entry, and if changed update V16/V17 and `docs/API.md`. |
| V-5 | Low | `apps/api/src/rate-limit.ts:15` (`CALL_IDLE_MS`), `apps/voice/src/call.ts:16` (`IDLE_MS`), `supabase/migrations/20261028100200_voice_calls.sql:72` (`interval '3 minutes'`) | The 3-minute idle window is defined three times (two TS constants, one SQL literal), tied only by comments. One shared constant in `@va/core` (or `@va/db`) for the two TS sites, and a test or comment that names the SQL literal. |
| V-6 | Low | `packages/core/src/sinks/spoken.ts:108` (`void releaseHold()`), the hold timer | An abort disarms nothing on the sink: the loop returns silently on a barge-in, so an armed 200 ms hold still fires after `runVoiceTurn` has returned, `sink.spoken` grows, and `releaseHold` is `void`-called with no catch (a throwing `say` would be an unhandled rejection). Also: `JSON.stringify` *returns* `undefined` (no throw) for a function or Symbol output, so `toolResultBlocks` (`packages/core/src/loop/tool-round.ts:123`) still writes a `tool_result` block with no `content` — no crash now, malformed row; normalise in `serialisableOutcome`. |
